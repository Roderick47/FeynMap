# Repository snapshots and persistence

Phase 2A changes FeynMap from an analyzer that must rebuild a graph for every consumer into a system that can analyze once and query a stored, verified repository snapshot many times.

## Why snapshots come before MCP

An MCP server should not parse the entire repository every time an AI asks `find_callers` or `validate_claim`.

The intended flow is:

```text
repository
    ↓
FeynMapEngine.analyze()
    ↓
SemanticGraph
    ↓
capture repository identity + file inventory
    ↓
immutable RepositorySnapshot
    ↓
SQLite SnapshotStore
    ↓
current snapshot pointer
    ↓
query / context / MCP requests
```

MCP therefore becomes a query surface over a known snapshot rather than a hidden source-code reparsing loop.

## CLI

From a repository root:

```bash
feynmap snapshot .
```

The default store is:

```text
.feynmap/snapshots.sqlite
```

The `.feynmap/` directory is excluded from both Git and the repository content inventory, so creating a snapshot does not change the content hash of the repository it describes.

Language and framework selection are part of snapshot identity:

```bash
feynmap snapshot . --language python --framework none
```

A custom store can be supplied:

```bash
feynmap snapshot . --store /path/to/feynmap-snapshots.sqlite
```

The command prints compact snapshot metadata and marks the captured snapshot as current for its repository.

## Snapshot identity

A `RepositorySnapshot` records:

- `snapshot_id`
- `repository_key`
- sanitized repository locator
- local root hint
- Git revision when available
- sorted file/content inventory
- repository content hash
- semantic graph hash
- semantic graph schema version
- analysis options
- creation timestamp

The immutable `snapshot_id` is derived from:

```text
repository_key
+ Git revision
+ repository content hash
+ semantic graph hash
+ semantic graph schema version
+ analysis options
```

Creation time and the SQLite store path are deliberately excluded from identity.

Two captures of the same checkout, graph and analysis options therefore produce the same snapshot ID even if captured at different times.

## Repository content inventory

Every normal repository file is fingerprinted using SHA-256 over its bytes. Generated/cache directories are excluded, including:

- `.git`
- virtual environments
- `node_modules`
- Python caches
- `.feynmap`

The sorted fingerprint list produces the repository `content_hash`. This file inventory is the foundation for later incremental analysis because FeynMap can compare two inventories and identify exactly which files changed.

## Graph serialization

`SemanticGraph` now supports lossless reconstruction with `SemanticGraph.from_dict()`.

Deserialization restores:

- node/edge enum types,
- source locations,
- evidence objects,
- attributes and metadata,
- graph indices,
- diagnostics.

Schema and schema-version mismatches are rejected rather than silently accepted.

Diagnostics generated by adapters are preserved when the graph is serialized; structural validation diagnostics are merged with them.

## Immutable store

`SnapshotStore` uses Python's standard-library SQLite support.

The `snapshots` table stores immutable snapshot metadata, file inventory and serialized graph. Saving a known snapshot ID with different content is rejected as an immutable-ID collision.

A separate `current_snapshots` table maps each `repository_key` to the snapshot that normal queries should currently use.

This separation is important:

```text
immutable history
    snapshot A
    snapshot B
    snapshot C
         ↑
         │
current pointer
```

Moving the current pointer does not mutate historical snapshots.

Stored graphs are hash-verified when loaded.

## Security / privacy

Git HTTP(S) remote URLs are sanitized before becoming repository locators. Userinfo such as embedded credentials or tokens is removed before the locator is stored or hashed.

The local root is retained only as a `root_hint` for local tooling; it is not used as the repository key when a Git origin is available.

## Current limitation: clone-independent graph identity

Repository identity and file-content identity are designed to be stable, but the current semantic graph still contains a repository-root node whose ID and selected metadata are derived from the absolute analysis path.

As a result, two different local clones of the same repository and commit can currently produce different `graph_hash` values and therefore different `snapshot_id` values.

This does **not** break local persistence, current-snapshot lookup, or snapshot-aware MCP on one checkout. It does mean FeynMap must normalize repository-root semantic identity before snapshots can be safely used as a cross-machine/shared cache key.

That normalization is part of Phase 2A hardening, not something the snapshot implementation should conceal.

## Next steps

The next Phase 2A work builds on this store:

1. normalize repository-root identity so semantic hashes are clone-independent,
2. compare file inventories between snapshots,
3. implement semantic graph diffing,
4. use changed files to support incremental analysis,
5. build token-budgeted context primitives over a stored snapshot,
6. expose the stored graph through the Phase 2B MCP grounding service.
